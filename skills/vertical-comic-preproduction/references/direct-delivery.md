# 分工直接交付合同 direct_delivery_v2

新分工交付默认采用本文。它收紧ZIP交接的发布标准：全话资料闭合，而非一格就绪即可发布；技术编译在批准前完成，接手人自动绑定，不再承担补件。常规单机模式和旧RV按原冻结版本运行；本次规则不为既有候选授予批准。

## 前期完成后才能交

历史适用范围先由[任务来源](task-origin.md)确定。下文“历史未知、预算、旧图”只约束本任务及明确选定继承的成果；同书同话另一次独立制作不自动继承。fresh必须核清本任务实际调用，不要求恢复无关旧账。资产候选调用另列，0正文调用不等于0资产调用。

在A资料及B/包最终审查前补齐全部技术字段：readiness、源适配、站位/可见性、准确前序、规则执行、细节、NOT_RUN计划、参考职责及不超过5条实际路径。冻结后不能再把这些字段补全称为“仅换哈希”要求生产接手人确认。

每话完整源序必须全部落到以下可生产状态：H001获批就绪；H002资料准备齐全；或有真实前格实图/首次高风险状态确认的内部生产依赖。历史未知、预算未核清/耗尽而无有效追加授权、旧图缺失或适用性未审、未批准场景、缺参考、源适配及工具不兼容都属于前期未完成。即使其他话有就绪格也不能把它们夹在正式包里。诊断候选可保存，但交接结论须明确“未交付”。

仅对用户明确选择沿用的旧图实际对照本次A/B，携原图、QA、验收来源和当前版本适用性复核；不为fresh主动找旧图。原任务需重生成且额度已耗尽时，集中说明准确格号并取得追加授权，不把调用归零。同任务UNKNOWN不能改标签为普通依赖或借换RV清除；独立重做不导入其他任务的UNKNOWN。

仅允许包内已批准格的真实前格实图/高风险实图确认留待生产补齐，必须是严格前序、无循环，完整登记补齐计划、参考槽位/哈希更新及批准边界。H001人工确认后才提交H002仍是固定停点，不因“直接交付”取消。

## 一次最终执行输入审查，避免分次签哈希

1. 前期先编译完整最终执行输入，技术检查可用candidate形成审查材料，但candidate不允许生产。真正变化的参考数组/职责段/镜头元数据一次并入本批最终审查；未变视觉不重审。
2. 索引设置delivery_policy=direct_delivery_v2，填齐下述最终输入及运行模板。用`handoff_zip.py review --root <候选目录>`生成最终输入摘要。摘要涵盖准确话格/半话、历史和依赖范围、原稿/实际源快照、A/B、生图包审查清单及冻结规则工具；不含事后追加的用户消息回执。
3. 按原A/B/生图包职责取得真实批准。最终B与包可合并提问并说明：“批准本最终执行输入；输入不变且真实接包演练通过后直接发布正式ZIP。”用户真实确认后分别记录原A/B/包批准和条件导出授权，不能从批准B推导包批准、不能伪造旧消息。
4. 写入实际批准证据及已核对历史，建立候选ZIP。用extract→bind→rehearse自动演练。全部原门禁通过、摘要未变，按已有条件导出授权直接release，不再单问一次ZIP哈希。用户若要求单独审核ZIP，则仍使用原精确ZIP/报告确认方式。
5. 若改变实际提示词/参考/设计/规则/交付话格或历史预算结论，摘要变化，必须回到准确受影响范围审查；不能“技术自动复用”扩大批准。仅新机器运行地址改变不改变摘要，也不重签旧批准。

条件导出授权JSON必须引用真实人类消息，字段为：status=APPROVED、source_kind=user_message、source_locator、quote、authorization_mode=approved_inputs_auto_export_v1、package_id、approved_input_digest、after_successful_rehearsal=true。程序核对范围与哈希，不能鉴别消息真实性。当前修改Skill的授权不等于批准E026/E028候选。

## 可移植输入及自动接包

新包在取得最终批准前使用以下两种明确格式，旧批准不原地迁移：

- 单格执行packet顶层加`portability_policy=approved_relative_inputs_v1`。生图审查签名以实际单格包根为基准保存参考相对路径，保留实际图像SHA256、原顺序、完整prompt、输出规格和现有画面约束。实际请求仍发送本机绝对路径。换素材/顺序/提示词仍使批准失配。
- 前格设计上下文在生成时用`continuity_context.py --portable`。来源root以该上下文JSON文件所在目录为基准，标记root_mode=context_relative_v1；读入时只在内存解析成本机绝对路径，原批准JSON不改字节。源稿、A/B版本和批准范围检查照常。多话来源登记需使用与上下文相同的可移植定义，不通过新场景标签绕过跨话。

规则记忆在前期冻结前给state/镜头/执行包中相同memory_source都附真实index_sha256；索引已包含规则正文哈希。移机时只允许root/runtime_snapshot地址改变，索引/正文/读取策略仍逐项验证，不读取已不存在的旧根，也不重签批准。未附内容身份的旧来源仍按原严格合同，不自动猜测复用。

模板中其余生产材料采用现有明确相对引用；不能留下依赖前期电脑的绝对运行根。包内运行模板是最终批准依据的执行视图，不可由生产人员重新编译一版再确认。

每话附加字段（均为包根相对路径+SHA256引用）：source_script、production_source_snapshot、visual_basis、shot_manifest、generation_review_packages数组、run_template。保留原ZIP索引source_snapshot的源序核对用途；production_source_snapshot指真实原门禁使用的源快照。

run_template指向JSON：

```json
{
  "policy":"portable_run_template_v1",
  "episode_id":"E026",
  "root":"E026/本地运行模板",
  "state_file":"00_输入审计/生产流程.json",
  "files":[{"path":"模板根下实际文件相对路径","sha256":"实际哈希","bytes":123}]
}
```

files完整覆盖模板根的实体，与当前冻结工具字节一致；模板清单本身放在模板根之外。生产模板保留源原文/序号、批准原件、预算与UNKNOWN、真实请求和返回记录，不得为了让bind成功而清空历史。

`handoff_zip.py bind --package-root <解压后包根> --run-root <包外新RV>`先验证全部模板/工具/规则，建立每话独立目录和本地绑定索引，只更新本地状态的runtime_snapshot、toolchain和适用memory_source根地址；工具及规则内容哈希不变，不改其他JSON，不生成批准，不变更预算。遇到别的旧绝对路径/合同不兼容必须在前期处理好再重演，不临时全局替换路径。

rehearse对每话运行冻结工具的H001真实compile、全话真实readiness及全话非candidate实际compile（全部只读，0次生图）；H002只编译核验，不提交、领许可或假造H001实图确认。实际A/B/包和源快照须等于最终审查输入，自动绑定证据须对应当前状态。首半话就绪不能掩盖H002未准备。已声明为正常生产依赖的格，其准备资料也必须通过readiness；实图依赖照原门禁等待。所有指定话均须检查，不能以其他话就绪代替。

## 接手人只执行固定步骤

1. 仅接收一个正式ZIP；用comic_start.py receive --zip <正式ZIP> --output <本机输出目录>先核对内置逐文件SHA256、CRC及演练/导出证据，再解压到新目录。交接说明包含在包内。旧版ZIP仍兼容其外部校验文件。
2. 从包内验证过的冻结工具执行bind建立全新本地RV。
3. rehearse核对本机路径/环境和批准范围；通过后按H001原许可/容量开始。无需人工重新批准地址绑定，不跳过真实门禁。
4. 保留高风险实图、H001与D人工审核；真正改变设计才按变更流程回前期。

接包说明必须填本次实际Python、包内工具路径和上述三条完整命令，不能让接手人自行研究目录。生产端若仍遇到准备缺项，视为前期交付缺陷，提交精确报告由前期新候选修复；不把无差别补件清单当成功交付。

这套合同减少的是可预先解决的往返，不保证生图服务永不异常或任何新机器环境都兼容。网络/服务故障和新实图质量问题按原运行异常流程处理，不能因此绕过审查。


新整话服装/配饰及单画面也须在前期闭合，见[具体合同](appearance-and-single-frame.md)：交付当前衣装核心、原板清晰裁区、身体佩戴位置、本格可见性/投影、frame_plan和实际prompt。不能把“生产时再猜首饰左右/补衣装来源”列为正常实图依赖。所有新增编译在最终输入审查前完成；旧包不自动套新哈希。
