# 人工审查停点与简短进度

## 当前整话模式：episode_async_v1

当前人工停点为A视觉基准、B全话镜头与全话生图包分别批准、真实高风险新状态确认、D最终整话验收；没有固定半话C。按真实进度显示“输入审计→A→B与包→整话生成/滚动自审→整话连续性→D”，不借旧8阶段编号冒充当前累计进度。等审消息第一行写话号、已完成/待补格数、待批准的精确范围与下一步；只用真实用户消息登记批准。例：

~~~text
【E021｜B镜头与生图包】整话30格，当前可审24格、待补6格｜状态：待分别确认B和包｜下一步：提交已批准就绪格
【E021｜D最终验收】整话30格实图和QA已齐｜状态：待人工确认｜下一步：逐格成品包
~~~

以下H001/H002、C及“8阶段编号”仅用于按旧半话合同恢复的RV。当前新任务读 [整话异步生产](episode-async.md)。

启用readiness_policy=panel_readiness_v1时优先按 [全话准备、逐格放行](panel-readiness.md)：全话总览保持完整，就绪设计和完整输入按准确范围集中交B及包审，缺口列待补；当前半话获批独立格可先生成。前格设计未定及真实图片依赖继续等待，C/D仍须完整。本文全话准备一次不要求无关缺口清零；未声明该策略的旧RV继续原完整准备门禁。

新初始化的完整v2任务启用 episode_preparation_v1 与 incremental_runtime_v1：全话资产/A、镜头/B、语义/比例及生图包各准备一次；H001/H002只划分实际生图、自审、修正和连续性审查。每话H001完成立即交C，C获批后H002沿原全话批准依据推进。具体执行见 [增量执行](runtime-efficiency.md)；旧RV按其原冻结合同恢复。

runtime可用“阶段3/8｜全话镜头＋全话生图包”合并展示、分别保存B和包批准。C只展示H001实际图与问题；C获批后直接开始H002，普通情况不再审镜头/包。某话C就绪立即交审，不等其他话。

当第2、3、6、8阶段或“生图包构建完成”因等待用户确认而暂停时，在用户可见消息的第一行显示简短进度，随后再给审查材料。总控汇总和单独阶段Skill都执行；这条人工停点显示本身不另派agent、不调用工具生成进度、不增加轮询或文件写入。普通生图、自审和已授权局部返修沿原流程推进。

长执行者的T1/T2由 [执行者两级监控](worker-watchdog.md) 处理，与人工停点提示分开。HUMAN等待不计执行者空闲；本话本地验收已完成时交回总控，由总控负责实际跨话实图复核和D，避免执行者在第8阶段反复等待其他话。

## 固定编号

保持8阶段编号，生图包确认为生图前的独立停点，不把后续阶段改成9阶段：

| 编号 | 阶段 | 对应人工审查 |
|---|---|---|
| 1 | 输入审计 | 仅未知或冲突项，沿原问题处理 |
| 2 | 视觉基准 | A |
| 3 | 镜头设计 | B |
| 4 | 第一半话生图 | 提交前另有生图包确认 |
| 5 | 第一半话自审与修正 | 沿原质量与修正合同 |
| 6 | 第一半话图片审查 | C |
| 7 | 第二半话生产与自审 | 沿已批准全话包推进；真实变更回相应A/B/包审查 |
| 8 | 整话、跨话验收及成品整理 | D |

编号描述当前审查对应的阶段，不是已获批准的累计数。准备完成但未批准，只写“准备完成／待审”，不写该阶段已经通过。第4、5阶段可返图即审并行，不因显示编号改回串行。

## 消息第一行

```text
【E021｜阶段2/8】视觉基准准备完成｜状态：待人工确认｜下一步：镜头设计
【E021｜阶段3/8】全话镜头与生图包就绪范围准备完成｜状态：待分别确认B和包｜下一步：H001生图
【E021｜阶段6/8】第一半话自审通过｜状态：待人工确认｜下一步：第二半话生产
【E021｜阶段8/8】全话验收包准备完成｜状态：待人工确认｜下一步：成品交付
```

下一步都以当前人工确认通过为前提，不能先提交再等回复。C后的下一步写“第二半话生图”，沿用原批准全话依据；出现真实新增或变更时注明受影响格和需重审版本，不推断其他话也已通过。

多话按实际停点逐话显示，只列发生变化、需要用户确认的话；不要用一个全局阶段代替五话不同进度。同一话A/B合并审查时可一行写“阶段2–3/8”，但分别记录真实批准。不要在进度行前加寒暄、标题或总结。进度行只是展示，不生成APPROVED、不更改生产状态。

## 生图包确认

新模式在H001首次正文/校准图前一次展示全话B镜头与全话生图包，分别获得真实批准。包准确覆盖整话源序；未到手的前格实图以批准的补齐方案表示，不能伪称已有图片。C通过后H002逐格实际输入仍运行完整技术门禁，但无需第二次包确认。旧RV按其原半话包批准恢复。

审查材料集中展示：整话源格范围、逐格最终提示词或准确实图依赖补齐方案、实际参考图及身份/当前衣装/场景/画风用途、输出规格和候选技术核对结果。待依赖格明确标为暂不可调用；生成时以真实前格输出补齐并再次完整预检。审查包准备齐后才询问。

在本话原审查记录保存真实用户消息、全话包版本/输入哈希及准确批准格范围；启用readiness时不得把部分批准扩大为整话。沉默、索引、模型自审或B批准不可补作包批准。同版本同范围的包确认复用；只有实际新增/变更的prompt、参考、镜头或状态才集中重审受影响内容。

有前格实图依赖时，前期冻结整话dependency_completion_plan_v1和全话包；仅允许把预留槽替换为已经真实QA通过的前格输出或逐字节副本。实际完整generate门禁仍核对所有参考、规则、身份、衣装、场景和画幅。方案之外的变化回包审查。

常规返修按原批准范围、诊断和唯一自动修正预算执行，不新增“每张返修包”停点；需要改变批准镜头、人物/衣装/场景、画风、规格或批准范围时，回原受影响A/B及包确认，集中审变化项。条件性高风险新状态确认与异常处理继续沿原合同，不用本进度规则免除。

这是一项Skill执行指令与消息格式约定。检查器generate技术PASS只表示技术通过；执行者和总控提交请求前另核对全话包的真实批准。新增preparation_policy字段只用于新RV，已在运行的任务按原冻结记录和用户授权处理。

启用readiness时，进度行同时标全话总数、当前半话完整可审/待补数和具体缺口；获批后另报真实提交、返回、合格数。部分包只确认明确列出的approval_panel_ids，不能写“整话已批准”。示例见panel-readiness.md。
