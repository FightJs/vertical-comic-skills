# 分工制作：前期导出与接包生产

用户明确指定“使用模式：分工制作”时读本文；本文是此模式的任务路由与交接合同，优先于其他文档中未限定模式的“整话直接生产、无半话C”。常规一机整话任务不改变，旧RV继续使用原冻结版本。仅提供两套启动模板供核对时不启动制作；实际执行须明确本次职责。

先按[任务来源](task-origin.md)区分独立重做、恢复与指定复用；分工只决定职责和窗口，不决定历史继承。本文所有“历史/旧图/预算”仅指本任务或用户选定继承的准确来源。fresh不携无关旧生产账，前期补资产调用与正文调用分开；接包、换RV继续原task_id。

新正式包采用[直接交付合同](direct-delivery.md)：前期先补完技术编译，最终B/包审查可连同不变输入的条件导出授权一次确认；全话准备及历史预算闭合后自动ZIP发布。接手端仅核验、bind和原门禁启动，不再临时补元数据并索要新哈希批准。

## 两种职责与结束边界

- **前期准备并导出交接包**：读取指定使用配置，按实际指定书/话核对源稿；完成全部指定话的输入审计、必要视觉基准A、全话镜头与比例/语义/实际依赖、两个半话的逐格候选生图包及交接预检。复用适用原批准，缺项按实际影响格标出；按原A、B/包审查要求提交。前期只获准完成这些工作；正文、正文首图和正文返修一律不调用，必要补资产另按原A授权范围。先形成技术完整的最终候选与差异表，取得最终输入批准及适用导出授权、完成自动接包演练后发布正式交接包，随后停在正文生图前。
- **接包生产与审核交付**：用户提供本机真实交接包路径、接手话号、生产审核人和输出目录；先接收核验，再建立新的本地运行。只复用版本/范围/内容确实适用的视觉基准、镜头和包批准。按本包半话窗口、实际依赖、原质量/规则和返修预算生成及验收。生产阶段由当前生图人员负责问题闭环，由指定审核人确认高风险实图、第一半话及D；需要改变设计时，当前生图人员集中整理准确变更并直接询问用户，不要求转交其他负责人或会话。

接包路径或输出目录仍为【填写…】占位时，仅列待填项，不猜路径、不把模板当执行请求。书/话与源稿/包不符须集中核对。指定E021–E025就是5话，格数/格序/文字来自实际源稿，不采用“大约30张”。

## 两半话是提交窗口，不是旧运行格式迁移

本模式声明collaboration_mode=split_production_v1、production_window_policy=reviewed_halves_v1，底层沿用当前episode_preparation_v1、episode_async_v1、scoped_episode_review_v1、comic_execution_v2与实际冻结runtime。不要把执行模式改成旧half_episode_async_v1或同时混入incremental_runtime_v1。上述分工字段是交接元数据/总控约束，不是现有CLI新增参数。

从准确源序分组：H001为前ceil(N/2)格，H002为余下格；30为15+15，35为18+17，N=1没有H002。源格号不重编。保留一份完整话镜头及生图依据，半话索引只是对该权威清单的有序引用，不复制第二套内容。

固定生产节奏：本地完整预检 → H001获批且就绪独立格持续并发 → 逐张自审及唯一一次自动返修 → 第一半话全部实际QA/适用连续性通过 → 生产审核人确认H001 → H002按同一批准依据生成/自审/限定返修 → 整话及适用跨话连续性 → D人工验收 → 逐格包。该半话停点由本模式总控显式执行，现有整话runtime不会自动创建它，不能把“整话就绪”当作H002放行。

每次领取许可、编译和实际提交均核对本半话源格集合。`production_runtime.py --action compile --panels <本半话准确格号>`只编译允许且就绪的选集；所有原门禁/真实许可仍执行。队列或自动提交器不能按本半话限制时，不使用整话批量自动提交；按本半话逐格领取原许可与编译，不能让第二半话在人工确认前进入实际调用。可以提前准备H002文本及包，但不能提前正文生图。交接索引中的半话批准需关联准确图/QA哈希，换图或换QA即重新核对；技术PASS不等于人工确认。

前格依赖与半话分组分开：普通顺序不伪造实图依赖；高风险、新状态单独确认和真实前格实图依赖仍保留。H001内真实前置返回并验收后可释放后格，不等整批结束；跨话依赖未齐只阻塞受影响格。半话并发受本机真实容量约束，不按包里前电脑容量虚报并发。

## 前期交接包内容与检查

正式交付仅一个自包含ZIP，交接说明、逐文件哈希清单及发布证据全部放入包内，不要求外置文件或嵌套ZIP；先执行[ZIP交接闭环](zip-handoff.md)的候选打包、全新目录解压、真实本地绑定和原冻结门禁演练，按已批准最终输入的条件授权直接发布，用户要求单独核对ZIP时再提交精确导出确认。前期负责验证可接包，不能把这一步留给生产首次发现。新增`交接验收索引.json`逐格核对源序、批准、历史调用/图/QA、返修余额和阻塞；`handoff_zip.py`是容器/演练工具，不替代原门禁或自动迁移器。

建议包结构；名称可适配已有项目，但语义及引用闭环必须完整：

```text
交接包_书名_版本/
  交接说明.md              # 实际接手步骤、就绪/待补表、预算与人工节点
  接包生产执行要求.md
  交接验收索引.json        # ZIP工具附加索引，不改原源/批准
  ZIP文件清单.json          # 工具生成
  历史调用及核对证据/       # 调用账、旧输出、QA与真实追加授权
  演练与导出确认/           # 正式发布时附原始预检及确认
  交接索引.json
  文件校验清单.json
  共用依据/             # 实际参考、源稿或完整锁定快照、共用批准与规则
  运行版本/             # 实际Skill/脚本及规则快照和校验清单
  E021/
    输入审计与源序/
    视觉基准/
    全话镜头与比例/
    逐格生图包/          # 唯一prompt、逐格JSON、参考图实体与职责
    半话索引.json        # H001/H002按准确源序引用
    前格依赖与补齐方案.json
    批准依据/
    待解决项.json
  E022/…
```

交接索引记录书/话、包ID/版本、源脚本/源快照版本与哈希、完整源格序、半话划分、各话依赖文件、规则和运行版本、审批范围及证据、生产人工审核节点、前期责任人与生产角色、已知缺口及禁止事项。每格须有原文、批准镜头/比例/当前人物衣装/首饰/场景、具体空间与接触、当前光照、背景保留省略、实际参考清单/顺序/用途和唯一最终提示词。

必须携带参考文件实体，不交本机绝对路径清单代替图片。可执行材料使用包根或逐格包根下明确约定的相对路径；在索引写清每个路径的基准。不可执行的历史批准原件保留原文和哈希，即使其中有旧电脑路径，也不能据此访问生产输入。对多话共享文件去重，但每话索引必须列出其依赖子集；只转交单话时一并复制该子集，不能缺共用目录。

实际前格补齐方案逐项写：当前话格、真实前置话格、为什么需要实图、前置验收条件、预留参考位置/顺序、补齐后哪一块文本/文件变化、再预检与批准复用边界。未知图片保留待补，不用占位PNG、候选图或“新场景”标签绕过依赖。参考合并/补前格后仍最多5条实际路径，不静默挤掉人物/画风依据。

导出前执行：文件/哈希和路径闭环；源格数/序与锁定文字；半话覆盖且不重不漏；批准来源和范围；画风与当前身份衣装/首饰参考；镜头比例/物理接触/光照/规则；实际参考解码/数量；跨格/跨话依赖和补齐；真实工具/规则冻结版本。调用原预检工具，不能自造“交接检查PASS”代替原门禁。无正文图时QA只可未审，不填视觉PASS。准备中缺口按受影响格记录，不妨碍无关格准备；正式直接交付前须全部消除前期缺口，正常内部实图依赖按已批准补齐方案保留。不能把局部可启动当全包交付完成。

A、B与包批准和导出确认分别记录，可由同一真实用户消息准确覆盖；未经确认的候选不得改成正式生产批准包。导出确认针对已展示的准确版本/清单，确认后修改即生成新候选版本并列变更，不覆盖原件。

## 接收、本地绑定与批准复用

1. 接受正式ZIP或其已解压包根。先核对内置清单与发布证据；ZIP按ZIP交接闭环安全解压到新目录，已解压目录通过同等内容校验后直接只读使用，不索回或重压原ZIP，阅读前期演练的准确就绪/待补范围；核对包ID、文件清单/哈希、书话范围、每话独立依赖、运行/规则快照、半话索引及真实批准依据。拒绝路径越界、缺参考和混合版本。先记RECEIVED_CHECKED，不等于正文可调用。
2. 保留收到的包只读，使用包内冻结handoff_zip.py bind和已核验运行模板，在新的生产RV建立本地状态和路径绑定。原有前电脑source/shot/prompt/批准文件按原字节保留，不原地改路径、重签旧哈希或伪造批准。只把执行时路径解析成本机真实绝对路径；不用前电脑的调用计划直接发送请求。
3. 对同一相对参考、同一内容哈希/顺序/用途、同一原文/镜头/规则的输入可复用适用原批准。另保存原包版本—本地文件—本地调用参数的映射与完整预检结果。仅路径解析不能作为换资产、换规则或变设计的理由。
4. 原编译器/门禁若不接受某一跨机来源或派生绑定，保持受影响范围HOLD，当前生图人员集中说明具体差异。direct_delivery_v2由bind解析已批准运行模板，不索要地址新哈希确认；旧格式若确需重编译，则在包外建立明确的新本地运行候选，真实执行输入有变时由当前生图人员按准确范围直接询问用户并取得批准；不能修改检查器、删除策略或把旧批准事件写成批准新哈希。完整实际预检和适用批准通过才记READY_FOR_H001。
5. 复用包内规则及冻结工具，不静默使用接包电脑安装的新版本；无可用快照或平台不兼容先查证，不能重建同名空快照。总控/唯一话执行者使用本机实际容量，按原单写和日志要求生产。

现有bind只自动复制已验证运行模板并解析runtime_snapshot/toolchain/memory_source地址，不重写创作输入、批准、历史预算或合并回传。新可移植签名/上下文应在正式交付前编译好并真实演练；旧包不具备该模板时，由当前生图人员在包外建立新本地运行候选，列出变化范围并直接询问用户，不在冻结包内猜路径或热修改。无法验证的来源须如实暂停，不以文档模式名授予许可。

交付演练中发现的不兼容、源冲突、漏账或缺图，须在新候选中修复并重演；只有用户明确缩小接手范围时才按新范围建立独立候选。生产接包后发现同类问题时，当前生图人员负责给出准确诊断、集中询问用户并在同一任务闭环；无法安全修复的受影响范围保持HOLD。原批准可复用范围不扩大，未变化视觉依据无需重新审批。

## 生产端问题闭环与回传

生产端按问题性质处理：生成结果偏离已批准方案时，按原自动返修预算和生产审核要求修回；路径、格式、缺资产、工具或历史账等技术/材料问题，由当前生图人员定位准确格号、缺项和可选处理方式后一次性询问用户；需要改变身份/衣装/画风/光照/场景布局/镜头/比例/背景模式/动作解法时，记录原版本、受影响格、原文问题、旧/新方案、依赖影响、需要更新的材料和批准范围，直接询问用户。

用户批准后，在包外本地生产RV保存变更记录或增量批准证据，只更新受影响且尚未提交的格，并重新执行相应输入签名、readiness、compile及批准门禁。生产保留旧版本、旧图、在途结果、调用历史、UNKNOWN和返修预算；只有受影响未提交格暂停，新版验收前不继续该范围。不覆写冻结包或旧批准，不重置自动返修轮次；新增生产授权或修正预算仍须用户准确确认。流程不要求交给其他负责人、创建外部任务或等待另一个会话返回新包。

回传至少含包ID/版本、准确格号/attempt/轮次、实际请求参数与参考哈希、原始返回PNG及哈希/尺寸、真实QA/适用规则观察、半话/D人工批准、异常/未知及变更关联。接收方把回传作为新证据导入，不覆盖原批准原件；结果未知不记完成也不直接重发。正式成品包只含当前获批图及源序索引，不含排版/气泡。

### 最终输入语义责任

新运行按[最终输入语义合同](final-input-semantics.md)把全话逐格核对放在前期：源稿、镜头、完整实际prompt、真实参考与检查判据全部对照。接包端完成本机核验与绑定后复用内容一致的审查，只复查实际变化、新实图和新异常；独立格继续。原半话及高风险/D人工节点保留。
